    payment_events(provider_event_id PK, payload jsonb, received_at)
  Bookings status extended: added REFUND_PENDING, REFUNDED to the CHECK constraint.
  WHY: We need a ledger (payments) so we can track charges and refunds against
       each booking, and a dedupe table (payment_events) so if a webhook fires
       twice we process it exactly once.

[B] THREE-PHASE PAYMENT (booking.service.js → payBooking)
  Phase A (SHORT TRANSACTION):
    - Lock the booking row (FOR UPDATE)
    - Require status = CREATED (concurrent duplicate requests fail fast)
    - Set status = PAYMENT_PENDING, extend hold by 3 min
    - Insert a payments row with status = INITIATED and a generated UUID as provider_ref
  Phase B (OUTSIDE TRANSACTION):
    - Call the payment gateway strategy (mockStrategy.processPayment)
    - If it throws → mark payment FAILED, revert booking to CREATED (safe retry)
  Phase C (FINALIZE TRANSACTION):
    - Lock booking row → lock payments row → lock show_seats (strict order: no deadlocks)
    - markBooked on show_seats WHERE booking_id = this booking AND status = 'HELD'
    - Row count must equal seat count → CONFIRMED
    - Otherwise (seats released/stolen) → REFUND_PENDING → trigger refund
  WHY THREE PHASES: Payment gateway calls can take 1-10 seconds. We MUST NOT hold a
  DB lock while calling an external API (network call inside transaction = deadlock risk
  + connection pool exhaustion). Phase A is a short 50ms transaction. Phase B is the
  slow call. Phase C is another short transaction.

[C] PROVIDER_REF (UUID as internal reference)
  - A crypto.randomUUID() is generated in Phase A as the provider_ref.
  - This UUID is passed to the gateway AND stored in payments.provider_ref.
  - WHY: Gives us a stable identifier to link the payment record to a webhook event
    even before the provider generates their own ID.

[D] WEBHOOK INGESTION (payment.controller.js + payment.service.js)
  Route: POST /api/v1/webhooks/payments
  - Mounted with express.raw({ type: 'application/json' }) BEFORE express.json()
    so the raw byte buffer is preserved for HMAC computation.
  - Verifies HMAC-SHA256 signature with crypto.timingSafeEqual (length-safe).
  - WEBHOOK_SECRET required in env.js (min 16 chars), never logged.
  - Deduplication + finalize in ONE transaction:
    INSERT INTO payment_events ON CONFLICT DO NOTHING → if conflict, return 200 no-op.
    If no conflict, run the same finalizePayment logic.
    WHY ONE TX: If finalize fails, the event row rolls back so the provider can retry.
  - Lock order everywhere: booking → payments → show_seats (prevents deadlocks).

[E] VALIDATIONS IN WEBHOOK
  - Look payment up by provider_ref (don't trust payload amounts blindly).
  - Amount mismatch → 422, no state change.
  - Unknown provider_ref → 200 ignored.
  - Valid state transitions only: INITIATED→SUCCEEDED/FAILED, SUCCEEDED→REFUNDED.
  - Late FAILED event after SUCCEEDED → ignored (never downgrade a confirmed payment).

[F] REFUND PATH (two-phase commit)
  Phase 1 (transaction): Set booking REFUND_PENDING.
  External call: Call provider refund (after commit, so DB lock is released).
  Phase 2 (transaction): Set booking REFUNDED + payment REFUNDED.
  If refund call fails → booking stays REFUND_PENDING (no data loss, retryable).
  retryRefund(bookingId): Admin/sweeper can retry stuck REFUND_PENDING bookings.
  WHY: We can't put the external refund call inside a DB transaction (same reason
  as payment: external network + DB lock = disaster). Two-phase commit keeps DB
  consistent even if the refund provider is temporarily down.

[G] ADMIN ENDPOINT: POST /api/v1/admin/retry-refund/:bookingId

  Looks up the latest payment row for the booking, re-runs executeRefund.

INTERVIEW Q&A FOR P2-M3:
  Q: "Why not put the payment call inside the database transaction?"
  A: "External network calls inside a DB transaction hold the row lock for the
  entire duration of the HTTP request to the payment gateway (could be 5-10 seconds).
  This would exhaust the DB connection pool under load and create deadlock risks.
  We use three-phase: Phase A (fast tx to set PAYMENT_PENDING), Phase B (gateway
  call outside any tx), Phase C (fast tx to confirm or trigger refund)."

  Q: "How do you prevent a webhook from being processed twice?"
  A: "We INSERT INTO payment_events (provider_event_id PK) ON CONFLICT DO NOTHING
  in the SAME transaction as the finalize logic. If the event was already processed,
  the INSERT returns 0 rows and we return 200 immediately. If the finalize step later
  fails, the event row rolls back too, so the provider's retry will process it again."

  Q: "What happens if a customer's card is charged but the server crashes before
  confirming the booking?"
  A: "The booking is in PAYMENT_PENDING with a payment row in INITIATED. When the
  webhook arrives (or when crash recovery runs lazily on next read), finalizePayment
  checks if the seats are still HELD by this booking. If yes → CONFIRMED. If the
  seats were released during the crash → REFUND_PENDING → we call the provider refund
  and mark REFUNDED. Money always goes back; seats are never double-booked."

--------------------------------------------------------------------------------
1. EXECUTIVE SUMMARY: WHAT IS PARALLELLOCK & WHAT PROBLEM DOES IT SOLVE?
--------------------------------------------------------------------------------
Imagine 10,000 users trying to book the exact same front-row seat for a blockbuster
movie at 10:00:00.000 AM.
In naive systems:
  - Worker 1 reads: "Seat is AVAILABLE".
  - Worker 2 reads: "Seat is AVAILABLE".
  - Worker 1 updates: "Seat is BOOKED by User 1".
  - Worker 2 updates: "Seat is BOOKED by User 2" (overwrites User 1!).
Result: Double-booking disaster (Check-Then-Act Race Condition).

ParallelLock solves this entirely inside PostgreSQL using:
1. Row-Level Locks (`SELECT ... FOR UPDATE`): Only 1 transaction gets the lock.
2. Ascending Seat Ordering (`ORDER BY seat_id ASC`): Zero deadlocks.
3. Fail-Fast Timeouts (`lock_timeout = 2s`): Aborts stalled locks before pool exhausts.
4. Passive Expiration (`now()`): No cron jobs required for seat release.
5. Idempotency Keys: Safe retries on spotty mobile connections.
6. Multi-Phase Payment State Machine (`PAYMENT_PENDING`): Gated duplicate charges.

--------------------------------------------------------------------------------
2. ARCHITECTURE BREAKDOWN: WHY EACH PIECE WAS USED & HOW IT WORKS
--------------------------------------------------------------------------------

[A] POSTGRESQL RELATIONAL SCHEMA (Strict Normalization)
- `users`: Stores customer accounts (Argon2id password hashing, JWT HS256 tokens).
- `theaters` & `screens`: Physical cinema locations and auditoriums.
- `seats`: Fixed physical seats with row, column, and tier (GOLD / SILVER).
- `movies` & `shows`: Film catalog and scheduled showtimes.
- `show_seats`: The INVENTORY table. Every show has a row per active seat.
  Status: AVAILABLE -> HELD -> BOOKED.
- `bookings`: Customer reservations and confirmed tickets.
  Status: CREATED -> PAYMENT_PENDING -> CONFIRMED (or CANCELLED / EXPIRED).

[B] DETERMINISTIC ROW-LEVEL LOCKING (`SELECT ... FOR UPDATE`)
- File: `server/src/modules/booking/showSeat.repo.js`
- Why: Guarantees that when multiple workers query the same seat, PostgreSQL
  puts concurrent transactions in a queue. Exactly 1 transaction acquires the
  lock; others wait. When the first transaction commits `status = 'HELD'`, the
  others read the updated status and immediately fail with `409 Conflict`.

[C] ASCENDING SEAT SORTING (`ORDER BY seat_id ASC`)
- Why used: Prevents DEADLOCKS.
  If User 1 locks Seat 10 then requests Seat 20, while User 2 locks Seat 20 then
  requests Seat 10, both wait on each other forever (Deadlock cycle).
  By enforcing `ORDER BY seat_id ASC`, both transactions ALWAYS request Seat 10
  first, then Seat 20. Deadlocks are mathematically impossible.

[D] FAIL-FAST CONNECTION TIMEOUTS
- Code: `SET LOCAL lock_timeout = '2s'; SET LOCAL statement_timeout = '5s';`
- Why used: If a transaction waits more than 2 seconds to acquire a lock, Postgres
  cancels it and returns error `55P03`. ParallelLock catches this and responds
  with `503 Service Unavailable` with `Retry-After: 1`. This prevents database
  connection pool starvation during massive traffic spikes.

[E] PASSIVE EXPIRATION (Zero Cron Sweeper Dependency)
- Code: `hold_expires_at <= now()` directly in SQL queries.
- Why used: Background cron jobs run once a minute; between cron runs, expired
  seats stay locked. ParallelLock evaluates expiration on-the-fly against the DB
  clock (`now()`). If User A's hold expired 1 millisecond ago, User B's query
  instantly treats that seat as `AVAILABLE`.

[F] IDEMPOTENCY KEY ENGINE (`Idempotency-Key` Header)
- Files: `002_idempotency.sql`, `booking.service.js`
- Why used: If a user taps "Pay" or "Hold" and their Wi-Fi drops, their phone retries.
  A partial unique index on `(user_id, idempotency_key)` ensures the retry returns
  the existing booking with header `Idempotency-Replayed: true` (HTTP 200) instead
  of double-charging or creating a duplicate booking.

[G] PAYMENT STATE MACHINE & CRASH RECOVERY (Milestone A0)
- Files: `003_payment_pending.sql`, `004_payment_recovery.sql`, `booking.repo.js`
- Why used:
  1. Window of vulnerability: Between sending a charge to Stripe/gateway and marking
     the booking CONFIRMED, a second concurrent click could read status = CREATED
     and charge the customer a second time.
  2. Solution: Inside transaction 1, flip status to `PAYMENT_PENDING`, record
     `payment_started_at = now()`, and extend the hold by +3 minutes.
  3. External payment runs OUTSIDE database transactions so external gateway delays
     never hold database row locks.
  4. Final transaction: Confirms booking ONLY if status is still `PAYMENT_PENDING`.
  5. Lazy Crash Recovery: If a server crashes mid-payment, reading or paying the
     booking after 2 minutes detects stale `PAYMENT_PENDING` under `FOR UPDATE`,
     reverting to `CREATED` (if hold valid) or `EXPIRED` (if hold expired).
  6. Unstealable Seats: While `PAYMENT_PENDING`, `lockSeatsForHold` treats seats as
     NOT free even if the original 8-minute hold passed. User B gets `409 Conflict`.

4. INTERVIEW DEFENSE: TOP 3 HARDEST QUESTIONS & HOW TO ANSWER
--------------------------------------------------------------------------------

Q1: "Why not just use Redis distributed locks (Redlock) for seats?"
Ans: "Redis locks add network hops, operational complexity, and split-brain risks.
PostgreSQL is already our source of truth. With `SELECT ... FOR UPDATE` ordered by
seat ID and a `lock_timeout = '2s'`, we get ACID transactional guarantees, zero
double-booking, and zero deadlocks directly in the database without any extra infra."

Q2: "What happens if a payment takes 15 seconds and the 8-minute hold expires?"
Ans: "When the user initiates payment, the server transitions the booking to
`PAYMENT_PENDING` in a short transaction and extends both `bookings.hold_expires_at`
and `show_seats.hold_expires_at` to `GREATEST(hold_expires_at, now() + 3 minutes)`.
Furthermore, `lockSeatsForHold` explicitly checks if `payment_started_at` is within
2 minutes. Competing users receive 409 Conflict and cannot steal the seat."

Q3: "What happens if the Node.js server crashes right after calling the payment gateway?"
Ans: "We don't need a heavy background cron job. We implement Lazy Crash Recovery:
Whenever the booking is subsequently read (`GET /bookings/:id`) or re-paid, the
server queries the row with `SELECT ... FOR UPDATE`. If status is `PAYMENT_PENDING`
and `payment_started_at` is older than 2 minutes, it checks if the hold is still valid.
If valid, it safely reverts to `CREATED`; if expired, it marks `EXPIRED` and frees
the seats. The recovery is completely atomic and race-safe."

WHAT WAS BUILT:

[A] DATABASE MIGRATION: 005_payments_and_webhooks.sql
  New tables:
    payments(id, booking_id, provider, provider_ref UNIQUE, provider_payment_id,
             amount_cents, status [INITIATED|SUCCEEDED|FAILED|REFUNDED], created_at, updated_at)
    payment_events(provider_event_id PK, payload jsonb, received_at)
  Bookings status extended: added REFUND_PENDING, REFUNDED to the CHECK constraint.
  WHY: We need a ledger (payments) so we can track charges and refunds against
       each booking, and a dedupe table (payment_events) so if a webhook fires
       twice we process it exactly once.

[B] THREE-PHASE PAYMENT (booking.service.js → payBooking)
  Phase A (SHORT TRANSACTION):
    - Lock the booking row (FOR UPDATE)
    - Require status = CREATED (concurrent duplicate requests fail fast)
    - Set status = PAYMENT_PENDING, extend hold by 3 min
    - Insert a payments row with status = INITIATED and a generated UUID as provider_ref
  Phase B (OUTSIDE TRANSACTION):
    - Call the payment gateway strategy (mockStrategy.processPayment)
    - If it throws → mark payment FAILED, revert booking to CREATED (safe retry)
  Phase C (FINALIZE TRANSACTION):
    - Lock booking row → lock payments row → lock show_seats (strict order: no deadlocks)
    - markBooked on show_seats WHERE booking_id = this booking AND status = 'HELD'
    - Row count must equal seat count → CONFIRMED
    - Otherwise (seats released/stolen) → REFUND_PENDING → trigger refund
  WHY THREE PHASES: Payment gateway calls can take 1-10 seconds. We MUST NOT hold a
  DB lock while calling an external API (network call inside transaction = deadlock risk
  + connection pool exhaustion). Phase A is a short 50ms transaction. Phase B is the
  slow call. Phase C is another short transaction.

[C] PROVIDER_REF (UUID as internal reference)
  - A crypto.randomUUID() is generated in Phase A as the provider_ref.
  - This UUID is passed to the gateway AND stored in payments.provider_ref.
  - WHY: Gives us a stable identifier to link the payment record to a webhook event
    even before the provider generates their own ID.

[D] WEBHOOK INGESTION (payment.controller.js + payment.service.js)
  Route: POST /api/v1/webhooks/payments
  - Mounted with express.raw({ type: 'application/json' }) BEFORE express.json()
    so the raw byte buffer is preserved for HMAC computation.
  - Verifies HMAC-SHA256 signature with crypto.timingSafeEqual (length-safe).
  - WEBHOOK_SECRET required in env.js (min 16 chars), never logged.
  - Deduplication + finalize in ONE transaction:
    INSERT INTO payment_events ON CONFLICT DO NOTHING → if conflict, return 200 no-op.
    If no conflict, run the same finalizePayment logic.
    WHY ONE TX: If finalize fails, the event row rolls back so the provider can retry.
  - Lock order everywhere: booking → payments → show_seats (prevents deadlocks).

[E] VALIDATIONS IN WEBHOOK
  - Look payment up by provider_ref (don't trust payload amounts blindly).
  - Amount mismatch → 422, no state change.
  - Unknown provider_ref → 200 ignored.
  - Valid state transitions only: INITIATED→SUCCEEDED/FAILED, SUCCEEDED→REFUNDED.
  - Late FAILED event after SUCCEEDED → ignored (never downgrade a confirmed payment).

[F] REFUND PATH (two-phase commit)
  Phase 1 (transaction): Set booking REFUND_PENDING.
  External call: Call provider refund (after commit, so DB lock is released).
  Phase 2 (transaction): Set booking REFUNDED + payment REFUNDED.
  If refund call fails → booking stays REFUND_PENDING (no data loss, retryable).
  retryRefund(bookingId): Admin/sweeper can retry stuck REFUND_PENDING bookings.
  WHY: We can't put the external refund call inside a DB transaction (same reason
  as payment: external network + DB lock = disaster). Two-phase commit keeps DB
  consistent even if the refund provider is temporarily down.

[G] ADMIN ENDPOINT: POST /api/v1/admin/retry-refund/:bookingId
  Calls paymentService.retryRefund(bookingId).
  Looks up the latest payment row for the booking, re-runs executeRefund.
  Returns 200 with { status: 'REFUNDED' } or { status: 'REFUND_PENDING' } if fails.

INTERVIEW Q&A FOR P2-M3:
  Q: "Why not put the payment call inside the database transaction?"
  A: "External network calls inside a DB transaction hold the row lock for the
  entire duration of the HTTP request to the payment gateway (could be 5-10 seconds).
  This would exhaust the DB connection pool under load and create deadlock risks.
  We use three-phase: Phase A (fast tx to set PAYMENT_PENDING), Phase B (gateway
  call outside any tx), Phase C (fast tx to confirm or trigger refund)."

  Q: "How do you prevent a webhook from being processed twice?"
  A: "We INSERT INTO payment_events (provider_event_id PK) ON CONFLICT DO NOTHING
  in the SAME transaction as the finalize logic. If the event was already processed,
  the INSERT returns 0 rows and we return 200 immediately. If the finalize step later
  fails, the event row rolls back too, so the provider's retry will process it again."

  Q: "What happens if a customer's card is charged but the server crashes before
  confirming the booking?"
  A: "The booking is in PAYMENT_PENDING with a payment row in INITIATED. When the
  webhook arrives (or when crash recovery runs lazily on next read), finalizePayment
  checks if the seats are still HELD by this booking. If yes → CONFIRMED. If the
  seats were released during the crash → REFUND_PENDING → we call the provider refund
  and mark REFUNDED. Money always goes back; seats are never double-booked."
