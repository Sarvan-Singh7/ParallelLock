1. EXECUTIVE SUMMARY: WHAT IS PARALLELLOCK & WHAT PROBLEM DOES IT SOLVE?
--------------------------------------------------------------------------------
Imagine 10,000 users trying to book the exact same front-row seat for a blockbuster
movie at 10:00:00.000 AM.
In naive systems:
  - Worker 1 reads: "Seat is AVAILABLE".
  - Worker 2 reads: "Seat is AVAILABLE".
  - Worker 1 updates: "Seat is BOOKED by User 1".
  - Worker 2 updates: "Seat is BOOKED by User 2" (overwrites User 1!).
Result: Double-booking disaster (Check-Then-Act Race Condition).

ParallelLock solves this entirely inside PostgreSQL using:
1. Row-Level Locks (`SELECT ... FOR UPDATE`): Only 1 transaction gets the lock.
2. Ascending Seat Ordering (`ORDER BY seat_id ASC`): Zero deadlocks.
3. Fail-Fast Timeouts (`lock_timeout = 2s`): Aborts stalled locks before pool exhausts.
4. Passive Expiration (`now()`): No cron jobs required for seat release.
5. Idempotency Keys: Safe retries on spotty mobile connections.
6. Multi-Phase Payment State Machine (`PAYMENT_PENDING`): Gated duplicate charges.
7. Background Advisory Sweeper (`pg_try_advisory_lock`): Housekeeping cleanup.
8. Immutable Line-Item Tickets (`booking_items`): Preserves audit trail.

2. ARCHITECTURE BREAKDOWN: WHY EACH PIECE WAS USED & HOW IT WORKS
--------------------------------------------------------------------------------

[A] POSTGRESQL RELATIONAL SCHEMA (Strict Normalization)
- `users`: Customer accounts (Argon2id password hashing, JWT HS256 tokens).
- `theaters` & `screens`: Physical cinema locations and auditoriums.
- `seats`: Fixed physical seats with row, column, and tier (GOLD / SILVER).
- `movies` & `shows`: Film catalog and scheduled showtimes.
- `show_seats`: INVENTORY table. Every show has a row per active seat.
  Status: AVAILABLE -> HELD -> BOOKED.
- `bookings`: Customer reservations and confirmed tickets.
  Status: CREATED -> PAYMENT_PENDING -> CONFIRMED (or CANCELLED / EXPIRED / REFUND_PENDING / REFUNDED).
- `booking_items`: Immutable ticket ledger per booking and seat.
- `payments`: Financial ledger tracking payment attempts and provider references.
- `payment_events`: Idempotent deduplication ledger for gateway webhooks.

[B] DETERMINISTIC ROW-LEVEL LOCKING (`SELECT ... FOR UPDATE`)
- File: `server/src/modules/booking/showSeat.repo.js`
- Why: Guarantees that when multiple workers query the same seat, PostgreSQL
  puts concurrent transactions in a queue. Exactly 1 transaction acquires the
  lock; others wait. When the first transaction commits `status = 'HELD'`, the
  others read the updated status and immediately fail with `409 Conflict`.

[C] ASCENDING SEAT SORTING (`ORDER BY seat_id ASC`)
- Why used: Prevents DEADLOCKS.
  If User 1 locks Seat 10 then requests Seat 20, while User 2 locks Seat 20 then
  requests Seat 10, both wait on each other forever (Deadlock cycle).
  By enforcing `ORDER BY seat_id ASC`, both transactions ALWAYS request Seat 10
  first, then Seat 20. Deadlocks are mathematically impossible.

[D] FAIL-FAST CONNECTION TIMEOUTS
- Code: `SET LOCAL lock_timeout = '2s'; SET LOCAL statement_timeout = '5s';`
- Why used: If a transaction waits more than 2 seconds to acquire a lock, Postgres
  cancels it and returns error `55P03`. ParallelLock catches this and responds
  with `503 SERVICE_UNAVAILABLE`, protecting the connection pool from saturation.

[E] PASSIVE EXPIRY ON DB CLOCK (`now()`)
- Why used: Traditional systems run background cron jobs every second to free seats.
  Crons can lag, crash, or introduce race conditions.
  ParallelLock checks expiry inline in every query:
  `hold_expires_at > now()` (Active) vs `hold_expires_at <= now()` (Expired).
  If a hold has passed its deadline, the very next query treats the seat as AVAILABLE
  and re-assigns it immediately on the database clock without waiting for any cron.

4. MILESTONE P2-M3: PAYMENTS, WEBHOOKS & LATE PAYMENT
--------------------------------------------------------------------------------
- Migration `005_payments_and_webhooks.sql`:
  `payments` table, `payment_events` table, and `REFUND_PENDING` / `REFUNDED` statuses.
- Three-Phase Payment Execution:
  Phase A (short tx): Lock booking, set `PAYMENT_PENDING`, generate UUID `provider_ref`,
  insert payment `INITIATED`.
  Phase B (outside tx): Call external payment gateway strategy (no DB locks held).
  Phase C (finalize tx): Lock order `bookings` -> `payments` -> `show_seats`.
  Verify every seat is still HELD under this booking -> mark `BOOKED` and `CONFIRMED`.
  If seats were lost/stolen -> transition to `REFUND_PENDING` and execute external refund -> `REFUNDED`.
- Webhook Ingestion (`POST /api/v1/webhooks/payments`):
  - Mounted with `express.raw({ type: 'application/json' })` before `express.json()`.
  - HMAC-SHA256 signature verification with `crypto.timingSafeEqual` (length-checked).
  - Deduplication and finalization in ONE transaction (`ON CONFLICT DO NOTHING`).
  - Unknown provider_ref returns 200 ignored. Amount mismatch returns 422.
  - Late FAILED event after SUCCEEDED is ignored (never downgrades confirmed payment).
- Refund Path:
  Two-phase commit: set `REFUND_PENDING` in tx, call gateway refund outside tx,
  commit `REFUNDED` in second tx. `retryRefund(bookingId)` handles retrying stuck refunds.

5. MILESTONE P2-M4: STATE MACHINE, SWEEPER & INVARIANTS
--------------------------------------------------------------------------------
[A] Explicit Booking State Machine (`bookingStateMachine.js`)
  - Statuses: CREATED, PAYMENT_PENDING, CONFIRMED, EXPIRED, CANCELLED, REFUND_PENDING, REFUNDED.
  - Allowed Transitions:
      CREATED         -> PAYMENT_PENDING, CANCELLED, EXPIRED
      PAYMENT_PENDING -> CONFIRMED, CREATED, EXPIRED, REFUND_PENDING
      EXPIRED         -> CONFIRMED, REFUND_PENDING
      CANCELLED       -> REFUND_PENDING
      REFUND_PENDING  -> REFUNDED
      CONFIRMED       -> (Terminal)
      REFUNDED        -> (Terminal)
  - `assertTransition(from, to)`: Enforces that status changes are mathematically legal.
    Illegal transitions throw `409 INVALID_STATE`.

[B] Migration 006: `booking_items` Line-Item Ledger
  - Table: `booking_items(booking_id, show_id, seat_id, price_cents, PRIMARY KEY(booking_id, seat_id))`
  - Written inside the hold transaction (`createHold`).
  - Tickets and My Bookings read directly from `booking_items` joined with `seats`.
  - Guarantees financial and seat audit records are permanent even if show_seats change.
  - Added `updated_at` to `bookings` for sweeper housekeeping.

[C] Background Advisory-Locked Sweeper (`sweeper.js`)
  - Frequency: `SWEEPER_INTERVAL_MS` (default 30,000 ms).
  - Guarded by PostgreSQL advisory lock (`pg_try_advisory_lock`):
    If multiple server nodes run, only ONE node acquires the lock; others exit cleanly.
  - Batches of 200 with `FOR UPDATE SKIP LOCKED`:
    (a) Expires stale `CREATED` bookings (`hold_expires_at <= now()`) and releases `HELD` seats.
    (b) Recovers stale `PAYMENT_PENDING` (>2 min): if hold valid -> reverts to `CREATED`;
        if hold expired -> marks `EXPIRED` and frees seats.
    (c) Retries `REFUND_PENDING` bookings older than 1 minute using `paymentService.retryRefund`.
  - Non-blocking: Housekeeping only. If sweeper is completely stopped, correctness
    is 100% maintained via passive query checks.

[D] Invariant Verification Script (`scripts/checkInvariants.js` / `npm run check:invariants`)
  - Ensures zero data corruption across 3 mission-critical queries:
    1. Zero BOOKED seats without a CONFIRMED booking.
    2. Zero CONFIRMED bookings whose seat count differs from BOOKED show_seats.
    3. Zero HELD seats whose booking is EXPIRED, CANCELLED, REFUNDED, or REFUND_PENDING.
  - Automatically runs after concurrency stress tests to assert complete data integrity.

6. MASTER INTERVIEW DEFENSE: TOP QUESTIONS & BULLETPROOF ANSWERS
--------------------------------------------------------------------------------

Q1: "Why not use Redis Redlock for seat locking?"
Ans: "Redis adds external infrastructure, network hops, and distributed split-brain
risks. PostgreSQL is already our system of record. By using `SELECT ... FOR UPDATE`
with numerical seat ordering (`ORDER BY seat_id ASC`) and a 2-second lock timeout,
we get strict ACID isolation, zero double-booking, and zero deadlocks natively."

Q2: "Why use three phases for payments instead of doing it in one transaction?"
Ans: "Payment gateways take anywhere from 1 to 10 seconds to respond. If we call an
external API inside a database transaction, we hold database row locks open for seconds.
Under high concurrency, this saturates the connection pool and halts the entire server.
Three-phase separates concerns: Phase A (50ms tx) locks state to PAYMENT_PENDING;
Phase B calls the gateway outside all transactions; Phase C (50ms tx) finalizes seats."

Q3: "How does ParallelLock prevent duplicate webhook charges?"
Ans: "We execute `INSERT INTO payment_events (provider_event_id, payload) ON CONFLICT DO NOTHING`
in the SAME atomic transaction as the seat confirmation. If a duplicate event arrives,
the insert returns 0 rows and we return 200 immediately. If seat finalization fails,
the entire transaction rolls back, allowing the provider's retry to succeed."

Q4: "Why do we have both passive expiry and a background sweeper?"
Ans: "Passive expiry on the DB clock (`now()`) is our correctness guarantee—even if all
background jobs die, no customer can ever book an expired seat or get blocked by a stale hold.
The background sweeper is purely for housekeeping—it proactively cleans up orphaned rows
and retries failed refunds during off-peak times using `pg_try_advisory_lock`."
